## 2. 적용 방법

### 2.1 Supabase

1. `202610130000_f04_f05_f06.sql`을 `supabase/migrations/` 폴더에 넣습니다.
2. 현섭 공유본 README대로 `supabase db push`를 실행하면 공통 기반 → F-07·08·10 → F-04·05·06 순서로 적용됩니다.
   - CLI 없이 확인만 할 때는 대시보드 **SQL Editor**에 파일 내용을 붙여넣고 Run 해도 됩니다. "destructive operations" 경고는 `drop policy if exists` 같은 안전한 줄 때문이므로 그대로 실행하면 됩니다.
3. 적용되면 자동으로:
   - `ride_messages` 테이블이 **Realtime**에 등록됩니다 (채팅 실시간 수신).
   - **pg_cron**에 `gachita-ride-flow-timers` (매분) 작업이 등록됩니다.
   - 이미 있는 팟마다 **방장의 참여 행**이 없으면 채워 넣습니다.

F-07·08·10 마이그레이션이 없어도 이 기능은 동작합니다(신청자 별점·차단 표시만 빠짐).

### 2.2 Flutter

이 브랜치(`Wonwongyo`)의 `shared/flutter`에는 이미 반영돼 있습니다. 실행 방법은 공유본 README와 같고, 추가 패키지는 없습니다.

## 3. 동작 규칙 (회의 결정 사항 대응)

### F-04 참여 신청·승인

| 회의 결정 | 구현 |
|---|---|
| 신청 → 방장 승인 → 채팅방 입장 = 참여 확정 | `request_join` → `approve_applicant`. 승인 순간 채팅방에 "○○님이 들어왔어요" |
| 방장은 신청자의 별점·참여·노쇼 횟수를 보고 판단 | 신청자 관리 화면에 표시 (F-07 프로필 조회 사용) |
| 정원이 차면 자동 "모집 완료" | 승인 시 정원 도달 → `status = 'full'` |
| 강제퇴장: 출발 확인 전까지, 같은 팟 재신청 불가, 노쇼 기록 안 함 | `kick_participant` (`kicked_at` 기록) |
| 자진 퇴장: 출발 확인 전까지, 자리가 나면 다시 "모집 중" | `leave_ride` (신청 대기 중이면 신청 취소로 동작) |
| (제안) 방장은 나갈 수 없고 팟을 취소 | `cancel_ride` |
| 거절된 사람의 재신청 | **허용** (회의에서 정하지 않음 → 상의 필요) |

### F-05 그룹 채팅

| 회의 결정 | 구현 |
|---|---|
| 참여 확정된 사람끼리 대화 | 방장 + 승인된 참여자만 읽기·쓰기 (RLS) |
| 입장·퇴장·강제퇴장·출발·도착 안내는 자동 메시지 | `kind = 'system'` 메시지로 저장 |
| 출발 12시간 후 채팅방·대화 삭제 | 매분 작업이 삭제, 12시간이 지나면 읽기·쓰기 모두 차단 |
| 상단에 "n시간 후 삭제" 경고 상시 표시 | 채팅방 상단 주황색 안내 |
| 도착 확인 시, 삭제 1시간 전에 경고 한 번 더 | 시스템 메시지로 1회씩 |

### F-06 출발·도착 확인과 노쇼

| 회의 결정 | 구현 |
|---|---|
| 출발 시각에 출발 확인 창, 각자 "탑승했어요" | 출발 시각부터 채팅방에 "출발 시간이에요" 카드 |
| 전원이 누르면 출발 처리 | 모두 확인되면 `departed_at` 기록 |
| 누르지 않은 사람 → 이미 탄 사람에게 "○○님이 오셨나요?" | "왔어요 / 안 왔어요" 버튼 (`answer_absence`) |
| "안 왔어요" → 불참자(노쇼) 기록 | `no_show = true` |
| (피그마) 10분 안에 응답 없으면 참여 안 함 | 출발 시각 10분 뒤 미확인자를 노쇼로 기록하고 출발 처리 |
| 도착 확인 → 운행 종료 → 평가 요청 | 탄 사람 중 한 명이 "도착했어요" → `status = 'completed'`, `ended_at` 기록 → F-07 평가 열림 |
| (제안) 출발 처리 후 3시간 동안 도착 확인 없으면 자동 종료 | 매분 작업 |
| (제안) 출발 시각 후 아무도 확인 안 하면 1시간 뒤 노쇼 없이 종료 | 매분 작업 |

**시간 규칙은 한 곳에서 바꿀 수 있습니다:** SQL의 `companion_private.flow_setting()` (출발 확인 시작, 10분, 1시간, 3시간, 12시간, 1시간 전 경고).

## 4. 데이터베이스 변경

### 기존 테이블 `ride_memberships`에 추가한 필드 (모두 선택 값)

| 필드 | 의미 |
|---|---|
| `requested_at` | 신청 시각. 기본값 `now()` |
| `decided_at` | 승인·거절·강제퇴장 처리 시각 |
| `kicked_at` | 강제퇴장 시각. 값이 있으면 `status = 'reject'`이어도 재신청 불가 |

공유본의 상태값(`pending` / `approved` / `reject`)은 그대로 씁니다. 자진 퇴장과 신청 취소는 행을 지웁니다.

### 새 테이블 `ride_messages`

| 필드 | 의미 |
|---|---|
| `id` | 메시지 번호 (자동 증가) |
| `ride_id` | → `rides.id` |
| `sender_id`, `sender_name` | 보낸 사람과 보낸 시점의 이름. 시스템 메시지는 비어 있음 |
| `kind` | `text` 또는 `system` |
| `body` | 1~1000자 |
| `created_at` | 보낸 시각 |

앱은 `insert`를 직접 할 수 없고 `send_ride_message` 함수로만 보냅니다.

### 앱이 부르는 함수 (RPC)

| 기능 | 함수 | 설명 |
|---|---|---|
| F-04 | `request_join(p_ride_id)` | 참여 신청 (같은 요청 반복은 무시) |
| F-04 | `approve_applicant(p_ride_id, p_user_id)` / `reject_applicant(...)` | 방장 전용 |
| F-04 | `kick_participant(p_ride_id, p_user_id)` | 방장 전용, 출발 처리 전까지 |
| F-04 | `leave_ride(p_ride_id)` | 자진 퇴장 또는 신청 취소 |
| F-04 | `cancel_ride(p_ride_id)` | 방장 전용, 출발 처리 전까지 |
| F-05 | `send_ride_message(p_ride_id, p_body)` | 저장된 메시지를 돌려줌 |
| F-06 | `confirm_boarding(p_ride_id)` | 탑승했어요 |
| F-06 | `answer_absence(p_ride_id, p_user_id, p_present)` | 왔어요(true) / 안 왔어요(false) |
| F-06 | `confirm_arrival(p_ride_id)` | 도착했어요 |
| F-06 | `get_ride_flow_state(p_ride_id)` | 채팅 화면용 상태 (단계, 참여자별 탑승·노쇼, 마감 시각) |
| 공통 | `ride_flow_module_version()` | 이 마이그레이션 적용 여부 확인 |

오류는 `join_closed`, `kick_closed` 같은 코드로 돌려주고, 앱이 한국어 안내로 바꿉니다 (`ride_flow_repository.dart`).

## 5. 다른 기능과 맞물리는 부분

| 기능 | 내용 |
|---|---|
| **F-02 팟 등록** | 회의 결정대로 방장은 첫 번째 참여자입니다. 팟을 만들 때 방장의 `approved` 참여 행을 넣어 주세요. 빠져 있으면 이 기능이 알아서 채우지만, **넣을 때는 `on conflict do nothing`** 을 써 주세요. |
| **F-07 평가** | 평가 자격(승인·탑승·노쇼 아님, `completed`, `departed_at`·`ended_at`)을 이 기능이 기록합니다. 로컬 테스트에서 평가 제출과 프로필 집계(참여·노쇼 횟수)까지 확인했습니다. |
| **F-09 푸시 알림** | 신청·승인·강제퇴장·출발 확인·불참 지목·도착·삭제 예고 시점마다 채팅방 시스템 메시지가 생깁니다. 푸시 담당자는 이 지점(SQL 함수 안의 `post_system_message` 호출)에 알림을 붙이면 됩니다. |
| **F-10 차단** | 신청자 관리 화면에서 내가 차단한 신청자에게 "차단한 사용자" 표시 (공유본의 `list_my_blocks` 사용). 신청 전 경고는 공유본이 이미 처리합니다. |
| **F-11 요금 분담** | 채팅방 상단 카드에 1인 금액 자리를 비워 두었습니다. |

## 7. 직접 확인하는 방법 (계정 2개)

1. Supabase **Authentication → Users**에서 테스트 계정을 하나 더 만들고, SQL Editor에서 프로필을 등록합니다.
   ```sql
   insert into public.profiles (id, display_name)
   select id, '테스트2' from auth.users where id not in (select id from public.profiles);
   ```
2. 계정 A로 테스트 팟을 만듭니다 (F-02가 연결되기 전까지는 SQL). 출발 시각을 몇 분 뒤로 잡으면 출발 확인까지 볼 수 있습니다.
   ```sql
   insert into public.rides (host_id, origin_name, destination_name, capacity, departure_at)
   values ('계정 A UUID', '기숙사', '버스터미널', 3, now() + interval '5 minutes');
   ```
3. 계정 B로 로그인 → 팟 상세 → **참여 신청하기** → "승인 기다리는 중"
4. 계정 A로 로그인 → 팟 상세 → **참여 신청자 확인** → **승인** → 채팅
5. 출발 시각이 되면 채팅방 카드에서 **탑승했어요** → (한 명만 누르면) **왔어요 / 안 왔어요** → **도착했어요** → **함께 탄 사람 평가하기**

## 8. 공유본에서 발견한 것 (현섭 씨 참고)

- `lib/features/companion/screens.dart`의 `CompanionApplicantsPage`에서 "신청자 새로고침"·"다시 시도" 버튼이
  `setState(() => _future = _readApplicants())` 형태라 눌렀을 때 Flutter 오류가 납니다
  ("setState() callback argument returned a Future"). `setState(() { _future = _readApplicants(); });`로 고치면 됩니다.
  이 추가본에서는 신청자 화면을 `applicantsBuilder`로 교체하므로 실제로는 이 화면이 쓰이지 않습니다.
